# 弱网射击排查与修复（2026-09-11）

检查线上 revision 5213c94 的日志（约 UTC 14:01–14:29）：共 28 条 server.metrics，最多 2 个连接，模拟耗时 P99 最高约 0.284ms；1 次请求错误为未准备开局，2 次指令拒绝发生在对局终止附近，1 次跳过发送。存在异常关闭和重连记录，但关闭码不能证明是丢包。现有日志不含 RTT、输入排队和射击结果，不能倒推出玩家那几枪的确切网络状况，也没有证据表明 CPU 或 Web 渲染平台是主要瓶颈。

已确认并修复：

- 弹道过期依赖服务端帧推进，快照停更时重复绘制旧弹道。现在以本地单调时钟设定最多 100ms 生存期，并对快照重传去重；750ms 停更浏览器测试不再残留。
- 30Hz 输入只读取“鼠标此刻是否按下”，漏掉采样间的短点击。现在保存按下/松开边沿，过旧边沿 200ms 后作废，失焦清空；不改变武器射速或半自动规则。
- TCP 停顿后的连续旧输入按每 tick 一条慢慢执行，容易维持积压。现合并无动作、无开火/跳跃变化的连续输入到 3 条，保留离散动作和边沿顺序；动作密集队列仍受原 32 条上限约束。18 条连续输入测试从 18 tick 缩短为 3 tick。客户端未发缓冲超过 8KiB 或快照中断超过 500ms 时暂停输入/预测，恢复后发送当前操作，而非补发断档期间动作。
- 联机服务端瞄准每 tick 只靠近目标一半，而客户端枪口已经跟随鼠标，产生方向不一致。联机人类角色使用该指令的瞄准点，AI 和单人战役保持原逻辑。
- 服务端发送缓冲门槛由 512000 字节降至 65536 字节，跳过尚未排队的过期快照，避免继续堆积。已经进入 TCP 的字节不能撤回。

新增网络/武器日志见 SERVER_LOGGING.md。指标按原 60 秒汇总及断开时输出，不记录输入原文或凭据。输入语义更新后内容规则版本提升到 18，客户端与服务器必须一起升级。

## 技术选型结论

现阶段保留浏览器 + Phaser + WebSocket。弹道残留和短点击丢失属于应用实现问题；WebSocket 的可靠有序 TCP 则确实会在重传时产生队头阻塞，换桌面引擎但仍使用 TCP 并不能消除它。模拟应用层停顿不等同真实 TCP 丢包实验。

下一轮用新增日志区分高 RTT、抖动、输入超时/积压、有效射击以及命中但无伤害。当前命中回溯仍有 4 个 30Hz tick（约 133ms）的公平性上限，严重高延迟不能保证命中移动目标；本轮不直接扩大回溯窗口。若修复后实测仍显示持续传输排队，应先考虑缩小快照/增量同步，或将实时输入/状态迁移到 WebRTC DataChannel（不可靠/无序）或 WebTransport 数据报，房间控制保留可靠通道；这需要协议、部署和浏览器支持评估，而非整体重写游戏。
