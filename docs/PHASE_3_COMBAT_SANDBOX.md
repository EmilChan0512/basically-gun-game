## 核心目标

以 SFH1 v1.2.1 的 SWF、反编译脚本、必要的 P-code 核对和原版运行观测为依据，将现有 Movement Lab / Gun Lab 从实验实现推进到可追溯、可对照的原版行为复刻。下一阶段优先补齐原版行为证据和实现偏差，而不是按自拟规则扩展通用战斗沙盒。

Phase 2 的历史测试通过只说明现有实验逻辑能运行，不代表与原游戏一致。本文替代此前同路径中的“多角色战斗灰盒”建议；Phase 3 名称仍是本次工作阶段定义，未核对缺失的原始开发计划 DOCX。后续机器人与 3v3 也必须从原版规则出发。

## 实施顺序

### 3.0 建立源码与行为对照表

先创建 `docs/ORIGINAL_BEHAVIOR_MATRIX.md`，每项至少记录：原版版本与哈希、脚本/方法/行号及文件哈希、调用链、证据 ID、证据类型、适用条件、当前实现位置、偏差、待验证问题及验证办法。

证据必须区分 EXTRACTED、INFERRED、OBSERVED 和 TUNED。新增静态事实经人工核对后进入证据库；只有原版实际运行样本才能标为 OBSERVED。定位到字符串或参数并不代表完整规则已验证。

优先追踪以下链路：

1. `Stats_Guns → Guns → 具体 Bullet 子类 → Bullet → 伤害接收方法 → Unit 死亡 → Player 复活`。
2. `Player 输入 → Movement 更新 → 地形碰撞 → Unit 姿态/动画`。
3. 换弹开始方法 → 动画/帧脚本或其他调用方 → `reloaded`，以及切枪与主副武器弹药对象的关系。

修正 ACCEPTANCE 中仍写“无 SWF”的历史状态展示，保留历史记录并添加当前状态说明。`workflow-status.json` 的生成状态不能代替人工证据库的已审核事实数量；核对二者职责，避免引用过期状态。

### 3.1 原版运行观测与规则确认

使用现有 Ruffle 工作流运行同一 SWF，记录运行器版本、关卡、职业、等级、技能、武器、位置、输入、录像帧率和测量误差。优先选可重复且修正因素最少的条件；不得把带职业或装备倍率的结果解释为基础值。

- 移动：起步、制动、反向、跳跃高度/顶点/滞空、空中操控、台阶/攀爬和平台碰撞。
- 武器：USP 与一把源码确认的原版自动武器，测量按住/点按、连续射击间隔、空弹匣、换弹、备用弹药耗尽和切枪往返。
- 命中：射程、散布/后坐力、角色不同命中区域、地形与平台遮挡、多目标和伤害修正。
- 生命周期：死亡后输入、复活倒计时、出生位置及生命/弹药恢复。

源码、P-code 与运行现象冲突时记录冲突，检查更新顺序、条件倍率及 Ruffle 兼容性，不任选一种结果作为事实。本次尚未执行原版运行观测。

### 3.2 按已确认规则复刻

按对照表逐项修改现有移动与战斗模块，先完成 USP，再完成已确认的自动武器。范围内的弹药、换弹、切换、散布、射程、命中、伤害和复活必须有来源链路。

Phaser/TypeScript 是实现工具，不能反过来决定原版规则。原版 30 步更新与当前 120 Hz 物理的计时、取整、更新顺序必须显式映射；若现有碰撞或时间结构无法重现行为，应调整结构，并用对照结果验证。不能只将所有数值乘除 30 就宣布等价。

需要多目标、掩体或脚本输入时，作为原版规则验证设施加入。是否穿透、平台是否挡弹、是否自动换弹、换弹能否取消、切枪是否重置冷却，以及复活恢复什么状态，均由核对结果决定，不在本文预设。

TUNED 值只能作为未确认项的临时调试占位，并在界面/文档中可辨认；不能满足对应的复刻验收。美术、音效、姿态和动画时序也需要记录原版参考；影响换弹等逻辑的时间线属于本阶段必查范围。完整资源替换可后续推进，灰盒画面不算视觉还原完成。研究源码和原始导出仍与生产资产隔离。

### 3.3 对照验证与偏差报告

创建 `docs/REPLICA_COMPARISON.md`，逐项展示原版基线、复刻结果、条件、误差、证据 ID、样本位置和未解决偏差。测量样本保存在现有研究目录，公开文档只记录必要事实与可追溯定位。

离散规则（弹药变化、命中对象、伤害、状态转换、逻辑更新数）应一致；连续运动的容差应在改参数前根据坐标缩放、录像分辨率和采样误差确定并写入对照表，不能看到结果后放宽门槛。随机行为核对分布和依赖因素，复刻端可注入种子做回归，不要求原版与复刻共享随机序列。
